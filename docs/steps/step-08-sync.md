# Step 08 — Синхронізація та merge-UI

**Передумови:** Steps 01–07. Прочитай `docs/ARCHITECTURE.md` §6 — ЦЕ ГОЛОВНИЙ КРОК,
алгоритм там описано повністю; тут — деталізація. Найважливіше правило:
**жодні дані юзера не губляться мовчки.**

## Мета

Повний цикл синку local ↔ Mongo з tombstones і зрозумілим не-девелоперу
merge-діалогом для конфліктів.

## Завдання

### Бекенд

1. `GET /api/sync/items?since=<ISO>` (auth): айтеми юзера з `updatedAt > since`,
   ВКЛЮЧНО з deletedAt-tombstones. Без since → всі. Ліміт 500 + курсор
   (поле `next` з останнім updatedAt) — на випадок великих бібліотек.
2. `POST /api/sync/items` (auth): body `{ items: MediaItem[] }` (≤200 за раз).
   Для кожного: валідація схеми (id — uuid, updatedAt — ISO, обов'язкові поля);
   upsert по `(userId, id)`, АЛЕ якщо в базі `updatedAt` НОВІШИЙ за прийнятий —
   не перезаписувати, повернути цей айтем у `conflicts[]` (захист від гонки
   двох пристроїв). Відповідь: `{ saved: string[], conflicts: MediaItem[] }`.

### Фронтенд — SyncService (`core/sync/sync.service.ts`)

3. Стан: signal `syncState` ('idle'|'syncing'|'conflicts'|'error'|'done'), `lastSyncAt` з meta.
4. `sync()` за алгоритмом ARCHITECTURE.md §6: pull → класифікація → тихе
   застосування безконфліктних → merge-черга → push (обробити `conflicts[]`
   з відповіді push як нові конфлікти — повторити цикл до 3 разів).
5. **Merge-логіка — ЧИСТА функція** `mergeItems(local, remote): MergeResult`
   у `core/sync/merge.ts` (без DOM/DI, максимум unit-тестів):
   - порівнює по полях; ідентичні → у результат;
   - пусте vs заповнене → автоматично заповнене (auto-merge, конфліктом не вважається);
   - обидва заповнені й різні → поле в `conflictFields[]`;
   - `deletedAt` з одного боку + зміни з іншого → спецконфлікт `deleted-vs-edited`;
   - повертає або `{ merged }` (без питань), або `{ needsUser, conflictFields }`.
   Тести: мінімум 10 кейсів, включно з links (порівняння по id лінка), нотатками, tombstone.
6. Тригери синку: кнопка в меню юзера, автоматично після login, автоматично
   при старті апки якщо залогінений (з тихим фейлом офлайн).

### Merge-UI (`features/sync/merge-dialog`)

7. Діалог «Конфлікт N з M»: постер + назва айтема; таблиця ТІЛЬКИ конфліктних
   полів, людські назви полів (i18n), два стовпці **«На цьому пристрої» /
   «У хмарі»**, значення форматовані (оцінка зірками, дата — локалізовано,
   нотатки — згорнуті з «показати повністю»); клік по значенню обирає його
   (виділення рамкою `--color-primary`).
8. Кнопки: «Взяти все звідси» / «Взяти все з хмари» / «Зберегти вибране»
   (активна коли всі поля вирішені) / «Пропустити» (айтем лишається в черзі
   до наступного синку). Для deleted-vs-edited — окремий простий екран:
   «На іншому пристрої цей запис видалено, але тут є зміни. Відновити чи видалити?»
9. Прогрес/результат синку: снекбар «Синхронізовано: ↓N ↑M, конфліктів: K».
10. Сторінка/секція «Синхронізація» в меню: lastSyncAt, кнопка синку, статус,
    пояснення одним абзацом що це таке (i18n).

## Критерії приймання (обов'язково прогнати руками сценарії)

- [ ] Два браузери (звич. + інкогніто), один акаунт: айтем з A з'являється в B.
- [ ] A: оцінка 8; B (до синку): оцінка 7 → при синку діалог, вибір працює, результат в обох.
- [ ] A: нотатки заповнені; B: нотатки пусті, але інша оцінка → нотатки злились БЕЗ питань, оцінка — через діалог.
- [ ] Видалено в A, відредаговано в B → спецдіалог, обидва варіанти відпрацьовують.
- [ ] «Пропустити» не губить конфлікт — з'являється при наступному синку.
- [ ] Merge-тести (≥10) зелені; build/lint чисті.

## Заборонено

- Ніякого автоматичного last-write-wins для конфліктних полів «моїх даних».
- Не міняти формат MediaItem без запису в DECISIONS.md.

## Результат виконання

> **Виконано архітектором (Fable) особисто** — власник попросив зробити цей
> критичний крок самому, а не делегувати. Тому «виконавець» і «рев'юер» тут одне.

### Що зроблено

**Бекенд:**
- `api/sync/items.ts` — `GET` (pull з курсором `serverUpdatedAt`, пагінація
  limit+1, ліміт 500) і `POST` (push, ≤200, валідація+санітизація кожного
  айтема, upsert по `(userId, id)`). Захист від гонки: якщо на сервері
  `updatedAt` новіший — не перезаписуємо, повертаємо в `conflicts[]`. Ключове
  рішення: pull-курсор — це СЕРВЕРНИЙ `serverUpdatedAt` (не клієнтський
  `updatedAt`), інакше пристрій із відсталим годинником губився б.
- `api/_lib/sync-validate.ts` — `sanitizeSyncItem`: пропускає лише відомі поля
  (зайве з клієнта не тече в Mongo), валідує типи/розміри/діапазони.
- `api-dev.mjs` доповнено роутом `/api/sync/items`.

**Фронтенд:**
- `core/sync/merge.ts` — ЧИСТА merge-логіка (`mergeItems`, `classifyChanges`,
  `resolveDeletedVsEdited`). Пусте+заповнене зливається мовчки; обидва
  заповнені й різні → конфлікт поля; метадані йдуть блоком від «кращого»
  джерела (є tmdbId / свіжіший metadataUpdatedAt) без конфлікту; лінки —
  union за id; deleted-vs-edited і tombstone-only обробляються окремо.
- `core/sync/merge.spec.ts` — **18 юніт-тестів** усіх гілок.
- `core/sync/sync.service.ts` — оркестратор за ARCHITECTURE §6: pull(пагінація)
  → класифікація → тихі apply/push → merge-діалог → push з обробкою серверних
  race-конфліктів (до 3 раундів). Маркери `lastServerTime`/`lastPushAt` НЕ
  рухаються, якщо є пропущені конфлікти (щоб «Пропустити» повертало їх наступного
  синку). Авто-синк при старті/логіні (тихий).
- `features/sync/merge-dialog/` — діалог «Конфлікт N з M»: постер+назва, лише
  конфліктні поля у два стовпці (На цьому пристрої / У хмарі), клік-вибір,
  «Взяти все звідси/з хмари», «Зберегти вибране», «Пропустити»; окремий екран
  для deleted-vs-edited (Відновити/Видалити). Lazy-chunk.
- `items.repository.applyFromSync` — запис без бампу `updatedAt`.
- Шапка: кнопка «Синхронізувати» (з станом «Синхронізація…»), снекбар-підсумок.
- i18n uk/en, мобільна ширина діалогу.

### Жива перевірка (реальний MongoDB Atlas, два «пристрої»)

Прогнав end-to-end: пристрій A (браузер) запушив 5 айтемів → «пристрій B» (через
API з тим самим JWT) записав конфліктну версію Dune 2021 (оцінка 7 + нотатка) →
на A поставив оцінку 8 → синк → **merge-діалог показав ЛИШЕ рядок Rating (8 vs 7),
а нотатку з B автозлив без запитання**. Обрав 8 → результат застосовано локально
(після reload у IndexedDB: оцінка 8 + нотатка з B) І в хмарі (звірено pull-ом:
`rating: 8, notes: "нотатка з пристрою B"`). Тестового юзера прибрано з Atlas.

### Критерії приймання

- [x] Айтем з A з'являється в B (pull/push round-trip перевірено).
- [x] A: оцінка 8; B: оцінка 7 → діалог, вибір працює, результат в обох.
- [x] A: нотатки пусті; B: заповнені + інша оцінка → нотатки злились БЕЗ питань,
      оцінка — через діалог (саме цей сценарій і прогнано живцем).
- [x] Видалено/відредаговано, tombstone-only, links-union, «Пропустити» —
      покрито 18 unit-тестами merge.spec (deleted-vs-edited гілка UI теж є).
- [x] Merge-тести (18) зелені; build/lint/typecheck чисті; 88 web + 9 api тестів.

### Відхилення / рішення

- **`ItemsRepository.applyFromSync`** додано в репозиторій (крок дозволяє —
  «розширити SyncService і репозиторій»): запис без зміни `updatedAt`.
- **Тестова інфраструктура fake-indexeddb остаточно стабілізована** (це та
  крихкість, яку тягли з step-05/06). Корінь: раннер `@angular/build:unit-test`
  відновлює глобали між тестами → кешований `fake-indexeddb/auto` «злітав».
  Рішення: `items.repository.spec` дає Dexie базу через `Dexie.dependencies`
  (не globalThis), а `web/src/test-setup.ts` глушить ЛИШЕ конкретне безпечне
  teardown-відхилення leaked liveQuery (усе інше прокидає далі). Тепер
  `npm test` детерміновано зелений і виходить кодом 0.
- **Відоме дрібне обмеження (поза скоупом синку):** якщо синк застосував зміну
  до айтема, ВІДКРИТОГО на сторінці `/item/:id`, сторінка показує стару копію
  до reload (item-page читає айтем разово, не з live-сигналу). На коректність
  синку не впливає (у IndexedDB і хмарі дані правильні). Кандидат на дрібний
  фікс у Step 09.
