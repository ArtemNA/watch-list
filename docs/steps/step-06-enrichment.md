# Step 06 — Збагачення сторінки айтема (OMDb + де подивитись)

**Передумови:** Steps 01–05. Прочитай `docs/ARCHITECTURE.md` §4.
**Потрібно від власника:** OMDB_API_KEY у `.env.local` / Vercel env.

## Мета

Сторінка айтема стає «однією сторінкою з усім»: рейтинги з кількох джерел
(TMDB, IMDb, Rotten Tomatoes, Metacritic), «де подивитись» (TMDB watch
providers, регіон UA), свіжі метадані. Дані різних API зливаються по imdbId —
без дублікатів.

## Завдання

### Фікси зауважень власника після Step 05 (робити ПЕРШИМИ)

0а. **Локалізація метаданих при додаванні й перегляді** (баг: айтеми зберігались
   англійською незалежно від мови UI, бо `getDetails` не передавав `language`):
   - `TmdbApiService.getDetails(kind, id, language)` — додати параметр,
     `SearchService.addToLibrary` передає `languageForUi(поточна мова UI)`;
   - у модель айтема додано `metadataLang?: 'uk' | 'en'` (ARCHITECTURE §2) —
     `mapDetailsToNewItem` заповнює його мовою запиту; поле опційне,
     Dexie-міграція НЕ потрібна;
   - `metadata.service.refresh(item)` (завдання 3 нижче) викликає деталі
     мовою поточного UI і оновлює кешовані title/overview/genres +
     `metadataLang`. Тригер автооновлення (завдання 3) розширити умовою
     `item.metadataLang !== поточна мова UI` — тоді перемикання мови апки
     оновлює описи при відкритті сторінки айтема (офлайн — показуємо кеш);
   - оновити юніт-тести мапінгу.

0б. **Вибір статусу при додаванні з пошуку** (зараз завжди 'want'):
   на картці результату замість однієї кнопки — **split-кнопка**: основна
   «Додати» (= «Хочу подивитись», найчастіший кейс, один клік як і раніше)
   + стрілка, що відкриває MatMenu «Додати як: Дивлюсь / Подивився / Покинув».
   `addToLibrary(result, status)` приймає статус; якщо статус 'watched' —
   у снекбарі, крім лінка на айтем, текст-підказка «Постав оцінку». Той самий
   MatMenu-патерн перевикористати без дублювання розмітки (спільний компонент
   або ng-template). i18n uk/en. Юніт-тест: addToLibrary зберігає переданий статус.

### Основні завдання

1. `api/omdb.ts` — GET-proxy: `?i=tt...` → OMDb `?i=...&apikey=...`. Валідація:
   `i` має матчити `^tt\d+$`, інакше 400. `Cache-Control: s-maxage=86400`.
2. `core/api/omdb-api.service.ts` + мапер відповіді OMDb → `ExternalRatings`
   (Ratings[] парсити: "Internet Movie Database" → imdb number, "Rotten Tomatoes" →
   "85%", "Metacritic" → number). Unit-тест мапера (включно з відсутніми полями, "N/A").
3. `features/item/metadata.service.ts` — «оркестратор збагачення»:
   - `refresh(item)`: TMDB details (`append_to_response=external_ids,watch/providers,translations`,
     `language` = поточна мова UI, див. 0а) → оновити кешовані поля айтема
     (включно з title/overview/genres/metadataLang); якщо є imdbId → OMDb →
     externalRatings; `metadataUpdatedAt = now`. Через `repo.update`
     (updatedAt оновиться — це ок, метадані теж синкуються);
   - автооновлення при відкритті сторінки айтема, якщо `metadataUpdatedAt`
     старший за 7 днів, або відсутній, або `metadataLang !== мова UI`;
     плюс кнопка «Оновити дані» (з тултіпом коли востаннє). Помилки
     збагачення — тихі (снекбар), сторінка працює з кешу.
4. UI сторінки айтема:
   - блок рейтингів: TMDB / IMDb / RT / Metacritic (іконка-лейбл + значення;
     джерела без даних не показуються),
   - блок «Де подивитись» (з watch/providers, регіон UA, потім fallback US):
     групи «Підписка / Оренда / Купівля», логотипи провайдерів (TMDB image CDN),
     обов'язковий дрібний напис «Дані JustWatch через TMDB» (вимога TMDB);
     якщо даних нема — блок ховається,
   - лінк «TMDB ↗» і «IMDb ↗» (якщо є imdbId) у хедері айтема.
5. Айтеми, додані вручну (без tmdbId): показати кнопку «Зв'язати з TMDB» →
   відкриває пошук з підставленою назвою; вибір результату проставляє tmdbId
   та метадані в ІСНУЮЧИЙ айтем (не створює новий).
6. i18n uk/en, мобільна верстка, build/lint/тести.

## Критерії приймання

- [x] Додавання з пошуку при укр. UI дає айтем з українськими назвою/описом/жанрами;
      перемикання мови UI і відкриття сторінки айтема оновлює їх на іншу мову.
- [x] З пошуку можна додати одразу зі статусом «Подивився» (split-кнопка), і він
      відображається в бібліотеці з цим статусом.
- [x] Для популярного фільму видно ≥3 рейтинги і провайдерів перегляду.
- [x] Повторний захід на сторінку протягом 7 днів НЕ б'є в API (перевірити по network).
- [x] Ручний айтем можна зв'язати з TMDB, після чого він збагачується як звичайний.
- [x] OMDb-ключ не світиться у фронті.

**Відхилення від плану:**

- **`metadataUpdatedAt` НЕ проставляється при створенні айтема з пошуку** (`mapDetailsToNewItem`).
  У специфікації задача 0а мовчить про це поле при створенні, але якщо проставити його «зараз»
  одразу після TMDB-фетчу, тригер автооновлення (задача 3: «якщо metadataUpdatedAt відсутній»)
  ніколи не спрацює для щойно доданого айтема — а OMDb-рейтинги й watch-providers на момент
  додавання ще НЕ тягнуті (це виключно робота `metadata.service`, задача 3). Без цього рішення
  критерій приймання «для популярного фільму видно ≥3 рейтинги і провайдерів» не виконувався б
  одразу, а тільки через 7 днів. Рішення: `metadataUpdatedAt` лишається `undefined` до першого
  `metadata.service.refresh()` (спрацьовує автоматично при першому відкритті сторінки айтема,
  перевірено вручну — див. вище). Задокументовано тут, а не мовчки змінено у ARCHITECTURE.md.
- **`MediaItem.watchProviders` додано до моделі** — цього поля нема в ARCHITECTURE.md §2.
  Без нього критерій «повторний захід протягом 7 днів не б'є в API» неможливо виконати для
  блоку «де подивитись»: без кешу в самому айтемі кожен рендер сторінки або довелось би бити
  в TMDB, або блок «де подивитись» не працював би офлайн. Мінімальне розумне рішення за
  правилом з PLAN.md п.4; архітектор може перенести опис поля в ARCHITECTURE §2 при ревʼю.
- **Спільна TMDB-мапінг-логіка винесена в `core/api/tmdb-mapping.ts` і `core/api/tmdb-language.ts`**
  (title/originalTitle/titleUk/year/poster/overview/genres/runtime/imdbId, `languageForUi`).
  Раніше ці чисті функції жили тільки в `features/search/search-mapping.ts`; тепер їх
  використовують і `search-mapping.ts` (створення айтема), і нове `features/item/metadata-mapping.ts`
  (оновлення метаданих) — без цього довелось би дублювати ідентичну логіку мапінгу деталей TMDB
  у двох місцях. `search-mapping.ts` реекспортує `languageForUi`/`isFallbackLanguage`, тому
  існуючі імпорти з neї не зламались.
- **Юніт-тест «addToLibrary зберігає переданий статус» реалізовано як тест чистої функції**
  `mapDetailsToNewItem(..., status)` у `search-mapping.spec.ts`, а НЕ як окремий
  `search.service.spec.ts`. Причина: `SearchService` вимагає `ItemsRepository` через DI, тобто
  будь-який spec-файл, що тестує `SearchService`, транзитивно імпортує `AppDb`/Dexie як значення —
  а це ТОЧНО той сценарій, який Step 05 вже діагностував як причину race condition в
  `items.repository.spec.ts` при кількох spec-файлах, що чіпають Dexie одночасно (див.
  `step-05-tmdb-search.md`, розділ «Відхилення від плану»). Перевірено: з окремим
  `search.service.spec.ts` (навіть із фейковим `ItemsRepository` через DI-override — сам
  imports-граф файлу однаково транзитивно тягнув Dexie) `items.repository.spec.ts` падав
  нестабільно з `DatabaseClosedError`/`MissingAPIError`; після видалення файлу і перенесення
  перевірки статусу в чисту функцію — 63/63 стабільно зелено в 3 прогонах. Спроба `fileParallelism:
  false` через `vitest.config.ts` не допомогла (стало гірше — почав падати й `app.spec.ts`),
  тому відкинута. Це вже наявна крихкість тестової інфраструктури (Step 03/05), не нова
  проблема Step 06 — але спосіб її обходу тепер задокументований і тут.
- **`SearchService.linkToExistingItem`** спершу проставляє `tmdbId`/`kind` через `repo.update`,
  потім викликає `metadataService.refresh(item)` — той самий код, що й авто-/ручне оновлення,
  замість дублювання TMDB+OMDb фетч-логіки в `search.service.ts`.
- Дрібне: `TmdbApiService.getDetails` завжди запитує `watch/providers` в `append_to_response`
  (і для звичайного додавання з пошуку, і для оновлення метаданих) — простіше й дешевше, ніж
  параметризувати список полів окремо для кожного виклику; зайві дані просто ігноруються
  мапером там, де не потрібні (`mapDetailsToNewItem` їх не читає).

**Відомі обмеження:** формальний тест на `metadata.service.ts`/`item-page.ts` (Injectable-сервіс
з побічними ефектами і компонент) не написаний — покриті лише чисті функції (`metadata-mapping.ts`),
за тим самим паттерном, що й решта проєкту (сервіси/компоненти з side-effects тестуються вручну
в браузері, а не юніт-тестами, per ARCHITECTURE §10). Поведінка перевірена вручну з реальними
TMDB/OMDb API (див. вище).
