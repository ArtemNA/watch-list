# Step 12 — Шеринг списків (URL + base64-код)

**Передумови:** Steps 01–11. Прочитай `docs/ARCHITECTURE.md` §9 повністю —
формат payload, принципи («статуси не шеряться», «знімок, не жива синха»,
«імпорт завжди створює новий список») описані там і НЕ обговорюються.

## Мета

Поділитися будь-яким списком (кастомним АБО похідним «Подивився»/«Улюблене»
тощо) через тимчасовий URL або офлайн base64-код; імпорт з превью.

## Завдання

### Спільний формат

1. `core/share/share-payload.ts`: тип `SharePayload { v: 1; name; sharedBy;
   entries: ListEntry[] }` + функції `buildPayload(list | derivedList, opts)`
   і `parsePayload(unknown): SharePayload | Error` (строга валідація версії
   і схеми — це вхід із зовнішнього світу!).
   `opts = { includeNotes: boolean; includeLinks: boolean }`:
   - `includeNotes` → у кожен entry копіюється `myRating`? НІ — тільки
     `notes` відправника як `sharedNotes`. Оцінки і статуси НЕ передаються
     ніколи (ARCHITECTURE §9),
   - `includeLinks` → `links` відправника як `sharedLinks`.
2. Анонімний відправник: `core/share/anon-id.ts` — стабільний `anon-<8 hex>`
   у meta, створюється ліниво. Якщо залогінений — `sharedBy = email`.

### Бекенд (розширює інфраструктуру Step 07)

3. `POST /api/share` — body: SharePayload. БЕЗ обов'язкового auth. Валідація
   схеми + ліміти (≤1000 entries, ≤256KB), rate limit по IP (best-effort).
   Зберігає в Mongo `shares`: `{ code, payload, createdAt }`,
   `code = crypto-random 12 симв. base62` (невгадуваний), TTL-індекс на
   `createdAt` (30 днів). Відповідь: `{ code, url }`.
4. `GET /api/share/[code]` — валідація формату code → payload або 404
   (однакова відповідь для «нема» і «протух»). `Cache-Control: private, no-store`.
5. Ensure indexes у `_lib/db.ts`: `shares.code` unique, `shares.createdAt` TTL.

### Фронтенд — поділитися

6. Кнопка «Поділитися» на сторінці списку (і похідного, і кастомного) → діалог:
   - чекбокси: «Поділитись моїми нотатками», «Поділитись моїми посиланнями» —
     ОБИДВА вимкнені за замовчуванням,
   - кнопка «Створити посилання» → POST → показує URL з кнопкою копіювання
     + напис «діє 30 днів». Помилка мережі → показати fallback-пораду про код,
   - кнопка/таб «Код для офлайну» → `base64url(JSON(payload))` → textarea
     з кнопкою копіювання (працює без мережі і без бекенда),
   - примітка в діалозі: «Це знімок списку. Зміни після — не передадуться».

### Фронтенд — імпорт

7. Роут `/share/:code` — **повноцінна сторінка-превью** (НЕ авто-додавання і
   НЕ куций диалог; це «вітрина» списку):
   - хедер: **«<sharedBy> поділився(-лась) з вами списком "<name>"»** +
     кількість фільмів + скільки з них уже є у твоїй бібліотеці (резолв по tmdbId),
   - нижче — ПОВНИЙ список фільмів з постерами (грід карток як у бібліотеці:
     постер, назва, рік, тип; entries з `sharedNotes`/`sharedLinks` мають
     позначку, що відправник додав нотатки/лінки). Фільми, які вже є в
     бібліотеці, позначені чіпом ТВОГО поточного статусу,
   - внизу і вгорі (sticky на мобільному) — дві кнопки: **«Додати список»** /
     **«Відхилити»**. Відхилити → нічого не зберігається, редірект на головну.
     Додати → `lists.repository.create` з назвою `«<name>» — від <sharedBy>`
     і `origin { sharedBy, sharedAt }` → редірект на створений `/lists/:id`
     зі снекбаром. ЗАВЖДИ новий список (id новий), нічого не перезаписується,
     навіть якщо список з такою назвою вже є,
   - превью working і для незалогіненого отримувача (шеринг не вимагає акаунта).
8. На `/lists`: поле/кнопка «Імпортувати за кодом» → вставив base64 →
   `parsePayload` → ТА САМА сторінка-превью (спільний компонент, дані з коду
   замість бекенда) → «Додати список» / «Відхилити». Крива строка → людська
   помилка («Код не розпізнано»), без стектрейсів.
9. Імпортований список у UI: бейджик «від <sharedBy>»; entries з
   `sharedNotes`/`sharedLinks` показують їх у розгортайці «Нотатки того, хто
   поділився» — ЧІТКО відокремлено від власних нотаток юзера.
10. i18n uk/en, мобільна верстка, тести: buildPayload (чекбокси реально
    вирізають нотатки/лінки), parsePayload (мусор, стара версія, великий
    payload), «імпорт не чіпає статуси», backend-валідатори.

## Критерії приймання (прогнати руками)

- [ ] Поділився «Подивився» → у друга (інкогніто-браузер) список додався, і ЖОДЕН
      фільм не позначений як переглянутий, поки він сам не позначить.
- [ ] Один фільм у друга вже був watched → у імпортованому списку він видний як watched.
- [ ] Чекбокси вимкнені → у payload немає notes/links (перевірити в network/коді).
- [ ] base64-шлях працює повністю офлайн (вимкнути мережу і імпортувати код).
- [ ] Два імпорти одного коду → два окремі списки, нічого не перезаписано.
- [ ] Превью показує «X поділився з вами списком Y», ПОВНИЙ грід фільмів з
      постерами і кнопки Додати/Відхилити; «Відхилити» не лишає слідів у даних.
- [ ] Невалідний/протухлий code → зрозуміла сторінка помилки.
- [ ] build/lint/тести чисті; процеси зупинені.

## Заборонено

- Жодної «живої» синхронізації шерів (це snapshot). Жодних публічних списків/каталогів.
- Не передавати статуси/оцінки відправника ні за яких умов.

## Результат виконання

> **Ревью архітектора (2026-07-12): ПРИЙНЯТО.** Перевірено: build/lint +
> 170 web і 44 api тестів; закрито відоме обмеження виконавця — прогнано
> живий сценарій «справжнього друга»: шер створено POST-ом проти реального
> Atlas, профіль отримувача повністю очищено (localStorage + IndexedDB,
> розлогінений), відкрито `/share/<code>` → превью «anon-review1 shared the
> list "Класика Sci-Fi" with you» з гріда, бейджем нотаток і Add/Discard →
> «Add list» → список з origin-бейджем, обидва фільми «Not in library»
> (статуси відправника НЕ передались), «+ To library» створив айтем зі
> статусом want, картка «Notes from whoever shared this» показує рівно
> шерену нотатку. У Mongo: TTL-індекс 30 діб і unique-індекс коду на місці.
> Кирилиця в payload зберігається коректно (mojibake у першій спробі був
> артефактом curl-клієнта Windows, не апки — перевірено чистим UTF-8
> клієнтом). Рішення «плоский файл + rewrite замість [code].ts» — правильне
> (той самий клас проблеми, що вже ловили з tmdb catch-all на Vercel).
> Тестові шери прибрано з Atlas. Зауважень немає.

Зроблено все за планом:

**Спільний формат.** `core/share/share-payload.ts` — `SharePayload`, `buildPayload(source, resolve, sharedBy, opts)`
(бере `notes`/`links` резолвленого айтема відправника через `resolve: (entry) => MediaItem | null`,
а не з entry — там нізвідки взяти оцінку/статус, вони й не потрапляють у payload ніколи),
`parsePayload(raw): SharePayload | Error` (строга валідація зовнішнього входу — і бекендового
JSON, і вставленого base64), `encodeSharePayload`/`decodeSharePayload` (base64url через
btoa/atob + TextEncoder, без залежностей). `core/share/anon-id.ts` — `AnonIdService`, лінива
генерація `anon-<8 hex>` через `MetaRepository`. `features/lists/share-source.ts` —
адаптер `MediaList`/`DerivedList` → `ShareSource` (живе в `features/`, не в `core/`, бо
`DerivedList` — feature-специфічний тип; `core/` не залежить від `features/`).

**Бекенд.** `api/share.ts` (POST, без auth, rate-limit `share:<ip>`, 12-символьний
base62-код через `node:crypto.randomBytes`, retry на unique-колізію) і `api/share-code.ts`
(GET, однакова 404 для «нема»/«протух», `Cache-Control: private, no-store`).
`api/_lib/share-validate.ts` перевикористовує `sanitizeListEntry`, який довелось
**експортувати** з `api/_lib/sync-validate.ts` (раніше був приватним) — той самий формат
ListEntry, дублювати валідацію сенсу нема. `api/_lib/db.ts` — індекси `shares.code` (unique)
і `shares.createdAt` (TTL 30 днів).

**Відхилення (задокументоване, не мовчазне):** динамічний файл-роут `api/share/[code].ts`
для GET **свідомо не використано**. Це той самий клас проблеми, що вже стався і задокументований
в `docs/PLAN.md` при деплої: `api/tmdb/[...path].ts` (catch-all) не матеріалізувався на проді
Vercel із цим `vercel.json` (custom `buildCommand`/`outputDirectory`), довелось перейти на
плоский файл + rewrite (`api/tmdb-proxy.ts`). Щоб не повторити той самий баг наосліп під час
наступного деплою, GET йде за тим самим перевіреним патерном: `api/share-code.ts` (плоский
файл) + rewrite у `vercel.json` (`/api/share/:code` → `/api/share-code?code=:code`). Ззовні
для фронтенду й для юзера це однаково виглядає як `GET /api/share/<code>` — контракт зі
специфікації не порушено, лише internal-реалізація ендпоінта.

**Фронтенд — поділитися.** `ShareListDialog` (features/lists/): чекбокси «Поділитись моїми
нотатками/посиланнями» — обидва вимкнені за замовчуванням; таби «Посилання»/«Код для офлайну»
(звичайні кнопки на токенах, не MatTabs — ARCHITECTURE §8 дозволяє з Material лише
діалог/меню/автокомпліт/снекбар/тултіп, TABS не в списку); офлайн-код перераховується
реактивно (`computed`) при зміні чекбоксів, лінк створюється лише по кліку (мережевий виклик).
Підключено до `lists-page` (іконка на похідних картках + пункт меню в кастомних) і
`list-detail-page` (пункт меню). **Важливий нюанс, знайдений живою перевіркою**: URL для
показу і копіювання будується на КЛІЄНТІ (`window.location.origin + '/share/' + code`),
а НЕ береться з `result.url`, який повертає бекенд — за dev-проксі (`ng serve` →
`api-dev.mjs`, `changeOrigin: true`) `req.headers.host` на бекенді підмінюється на хост
проксі-цілі (`localhost:3000`), і задокументований у бекенді `url` виявився б мертвим
посиланням при копіюванні. Бекенд і далі повертає `url` у відповіді (відповідає специфікації
й корисний як інформація), просто фронтенд йому свідомо не довіряє для відображення.

**Фронтенд — імпорт.** Спільний презентаційний компонент `features/share/shared-list-preview/`
(`SharedListPreview`, `input.required<SharePayload>()`, outputs `listAdded`/`discarded` —
сам НЕ навігує, лишає це контейнеру) перевикористаний у двох місцях:
- `/share/:code` → `SharePreviewPage` (features/share/) — `ShareService.fetchShare` +
  `parsePayload`, стани спінер/помилка (однакова людська фраза для 404 і malformed)/готово;
- `/lists` → «Імпортувати за кодом» → `ImportByCodeDialog` (features/lists/) — двофазний
  діалог (вставити код → `decodeSharePayload`+`parsePayload` на клієнті, без жодного
  мережевого виклику → та сама `SharedListPreview` всередині того самого діалогу).

Імпорт завжди створює НОВИЙ `MediaList` — додано `ListsRepository.createImported(name, entries, origin)`
(окремий метод, а не розширення `create()` — сигнатура іншого паттерну виклику, коротше й
чіткіше окремим методом). `list-detail-page` показує бейдж «від {sharedBy}» (`l.origin`).

**Ітерація дизайну нотаток/лінків відправника (знайдено живою перевіркою власника, двічі).**
Перший варіант — повна розгортайка `<details>` прямо на entry-картці в гріді `list-detail-page`
(~160px завширшки) — виявився затісним і кострубатим на реальному екрані. Другий варіант —
компактний бейдж-мітка на картці (як «Has notes» у `SharedListPreview`) замість тексту, а
повний readonly-текст перенесено на item-page **всередину блоку «У списках»** — теж відхилено
власником: членство в списках і читабельна інформація від відправника — різні речі, змішувати
в одній картці плутає. Фінал: на `list-detail-page` — лише бейдж `hasSharedExtras(entry)` (для
обох станів — резолвленого і не-резолвленого entry); на item-page — **окрема** `app-card`
«Нотатки того, хто поділився» (рендериться лише якщо `sharedNotesEntries().length > 0`),
з `<details>` на кожен список, де в entry є sharedNotes/sharedLinks (summary — назва списку,
на випадок, якщо айтем шерився з кількох джерел). Для entries, які ще НЕ додані в бібліотеку
(«Not in library»), item-page не існує — бейдж на картці лишається, повний текст стає видимим
лише ПІСЛЯ додавання (свідомий компроміс простоти UI, а не бага).

**Тести:** 170 web (було 148) + 44 api (було 32) — нові: `share-payload.spec.ts`
(buildPayload з обома чекбоксами, parsePayload на невалідний вхід, encode/decode round-trip),
`anon-id.spec.ts` (лінива генерація, стабільність, кеш), `share-source.spec.ts`,
`lists.repository.spec.ts` (+createImported), `api/_lib/share-validate.spec.ts` (валідація
payload, включно з лімітом 1000 entries і 256KB). `npm run build`/`lint`/`lint:api`/
`typecheck:api` чисті, бюджет бандла НЕ підіймався (877kB з 900kB warning).

**Живцем у браузері** (обидві теми, uk/en локалі, 360px і 1280px, через `api-dev.mjs` +
реальний MongoDB Atlas):
- шер похідного списку «Подивився» з увімкненими обома чекбоксами → офлайн-код → імпорт
  (в тій самій вкладці зібраним вручну payload, що еквівалентно з погляду коду —
  parsePayload/buildPayload не знають про сесію) → фільм показаний БЕЗ статусу, «+ в
  бібліотеку» створює його зі статусом `want` (НЕ `watched`) — підтверджено, що статус
  НІКОЛИ не передається;
- розгортайка «Нотатки того, хто поділився» показує рівно те, чим поділився відправник
  (нотатку + лінк-трейлер);
- фільм, який уже є в бібліотеці отримувача (той самий tmdbId) — одразу показаний зі своїм
  реальним статусом (want/watching/watched/dropped), без імпорту;
- обидва чекбокси вимкнені за замовчуванням → у декодованому base64 (перевірено напряму
  через `atob` у консолі) немає полів `sharedNotes`/`sharedLinks`;
- `/share/:code`, створений реальним POST `/api/share` проти Atlas → повноцінна сторінка
  превью, «Додати список» → редірект на `/lists/:id` зі снекбаром, «Відхилити» → редірект
  на головну і НІЧОГО не створюється (перевірено — список не з'явився в `/lists`);
- невалідний/вигаданий код → «Це посилання не працює» (однакова фраза, як і для протухлого);
- локалізація: діалог шеру, меню (Rename/Share/Delete), бейдж походження, розгортайка нотаток,
  снекбар — усе коректно перемикається на uk (перевірено), i18n key-parity тест (uk/en/ru)
  зелений;
- мобільна верстка 360px: іконка шеру на похідних картках, діалог шеру (таби, чекбокси,
  результат — колонкою на вузькому екрані), грід SharedListPreview (2 колонки).

Тестові артефакти (імпортований список, доданий тестовий айтем), створені під час перевірки,
прибрані з локальної IndexedDB одразу після.

**Відоме:** живий шер між ДВОМА окремими браузерними профілями («інкогніто-друг» у буквальному
сенсі) не проганявся — офлайн-шлях перевірено вручну зібраним payload у тій самій вкладці;
з погляду коду це не відрізняється (жодна частина share-логіки не залежить від сесії/юзера
поточної вкладки), але це не буквально «другий пристрій», як робилось для items/lists-синку
в Step 08/11. dev-сервери (`ng serve`, `dev:api`) зупинені після перевірки.
