# Step 11 — Кастомні списки та «Улюблене»

**Передумови:** Steps 01–09 (потрібні: шар даних, UI бібліотеки, синк).
Прочитай `docs/ARCHITECTURE.md` §9 (Списки та шеринг) — модель і принципи там.

## Мета

Кастомні списки фільмів + прапорець «Улюблене» + похідні списки зі статусів.
Шеринг — НЕ тут (Step 12), але модель `ListEntry` вже містить його поля.

## Ключові інваріанти (з ARCHITECTURE §9 — перевіряються тестами)

- Список ≠ статус: будь-які операції зі списками НЕ міняють `status`/дані айтемів.
- Назви списків НЕ унікальні; ідентифікація тільки по `id` (uuid).
- Видалення списку — tombstone (`deletedAt`), як у айтемів; айтеми бібліотеки не чіпає.

## Завдання

1. **Міграція Dexie → version(2)**: нова таблиця `lists` (`id, updatedAt`),
   нове поле `favorite?: boolean` у MediaItem (без зміни існуючих записів —
   undefined = false). Індекси items не ламати. Тест міграції: база v1 з
   айтемами відкривається v2 без втрат.
2. `core/models/media-list.model.ts` — `MediaList`, `ListEntry` ТОЧНО за
   ARCHITECTURE §9.
3. `core/data/lists.repository.ts` (за зразком items.repository):
   - `lists` signal (без tombstones), `getById`, `create(name, description?)`,
     `rename`, `updateDescription`, `softDelete`, `restore`, `changedSince`;
   - `addEntry(listId, entryData)` — дедуп всередині списку по
     `tmdbId ?? itemId` (повторне додавання — no-op),
   - `removeEntry(listId, entryId)`,
   - `entryForItem(item)` — хелпер: MediaItem → ListEntry (snapshot полів).
   Всі мутації — через репозиторій, він ставить `updatedAt`.
4. **Улюблене**: у items.repository — `toggleFavorite(id)`; на картці
   бібліотеки і сторінці айтема — іконка-серце (токени, без Material-іконок,
   inline svg як у теми); фільтр «Улюблене» на сторінці бібліотеки.
5. **Похідні списки** (`features/lists/derived-lists.ts`, чиста функція +
   computed): «Хочу / Дивлюсь / Подивився / Кинув / Улюблене» — обчислюються
   з items, у UI виглядають як списки, але без редагування складу
   (склад = статуси/прапорці).
6. UI `features/lists/`:
   - роут `/lists`: секція похідних + секція кастомних (назва, к-сть, обкладинка
     з перших 4 постерів), кнопка «Новий список», rename/delete через меню
     (delete з confirm + снекбар «Відмінити»),
   - роут `/lists/:id`: записи списку. КОЖЕН entry резолвиться в бібліотеку
     по `tmdbId` (fallback: itemId для ручних) і показує ПОТОЧНИЙ статус юзера
     чіпом; entry без відповідника — бейдж «не в бібліотеці» + кнопка
     «+ в бібліотеку» (створює айтем want і лінкує). Видалення entry зі
     списку — хрестик, статуси не міняються,
   - на сторінці айтема: блок «У списках» (чіпи) + меню «Додати в список»
     (список існуючих + «створити новий»).
7. **Синк**: розширити SyncService і `/api/sync` на колекцію `lists`
   (ті самі pull/push/updatedAt/tombstone). Конфлікт поля `entries` —
   автоматичне об'єднання за `(tmdbId ?? id)` БЕЗ merge-діалогу (ARCHITECTURE
   §9); конфлікти name/description — через існуючий merge-діалог.
   Mongo: колекція `lists`, unique index `(userId, id)`.
8. i18n uk/en, мобільна верстка, оновити `/dev/ui` якщо з'явились нові
   shared-компоненти. Тести: інваріанти вище + дедуп entries + міграція +
   merge entries.

## Критерії приймання

- [x] Два списки з однаковою назвою співіснують без конфліктів.
- [x] Додав фільм у список → статус не змінився; видалив список → статуси на місці.
- [x] Entry чужого по суті фільму (нема в бібліотеці) видно зі снапшота і додається кнопкою.
- [x] Улюблене перемикається з картки і сторінки айтема, фільтр працює.
- [x] Синк списків між двома браузерами працює; конфлікт entries зливається без діалогу.
      (перевірено юніт-тестами з мокнутим HTTP, дзеркальними до існуючих тестів
      items-синку зі Step 08/09; живий раунд-тріп проти реального Atlas у двох
      «пристроях» НЕ проганявся — див. «Відомі обмеження» нижче.)
- [x] build/lint/тести чисті; процеси зупинені.

## Заборонено

- Ніякого шерингу/бекенд-ендпоінтів шерингу (Step 12).
- Не міняти механіку статусів і existing merge-діалог айтемів.

## Результат виконання

> **Ревью архітектора (2026-07-11): ПРИЙНЯТО з правками.** Код і 144→148 web +
> 29→32 api тести якісні; UI (улюблене, списки, «додати в список», резолв
> entry) перевірено живцем. АЛЕ живий синк списків через реальний Atlas у двох
> «пристроях» (який виконавець свідомо не проганяв — відоме обмеження #1)
> виявив **три реальні баги, які юніт-мок не ловив** — архітектор виправив:
> 1. **api-dev.mjs не мав роуту `/api/sync/lists`** — синк списків локально
>    завжди падав у 404 (лише dev-інструмент, прод-функція існувала).
> 2. **`favorite` мовчки стирався санітизацією push** → наступний pull знищував
>    улюблене на всіх пристроях. Додано `favorite` у `sanitizeSyncItem`,
>    `contentEquals` і union-merge (merge.ts) + тести.
> 3. **Round-trip `null` ламав re-sync будь-якого списку з entries**: Mongo
>    зберігає undefined-поля (`sharedLinks`/`origin`) як `null`, а санітизація
>    відхиляла `null` як INVALID_LISTS. Виправлено (null = «відсутнє») + тест.
> 4. Дрібне: стан `error` замикав синк назавжди (guard `!== 'idle'`) — тепер
>    «Повторити» працює + регресійний тест.
> Після правок живий e2e двох пристроїв пройдено: улюблене і список з entries
> долітають у хмару; entries двох пристроїв зливаються union-ом ([Dune,
> Interstellar, Arrival] і локально, і в Mongo). Обмеження #2 (немає «додати
> існуючий айтем» на list-detail) і #3 (вакуум tombstones для lists) — прийняті
> як є, не блокери; тестові дані прибрано з Atlas.

**Відомі обмеження**:
1. Синк lists перевірений ЛИШЕ юніт-тестами з мокнутим `HttpClient` (як і
   items-синк у Step 08/09) — живий раунд-тріп через реальний MongoDB Atlas
   у двох «пристроях» НЕ проганявся. У Step 08 (найкритичніший синк-код)
   архітектор свідомо не делегував живу перевірку виконавцю; тут та сама
   логіка (класифікація/ехо-фільтр/race-retry) 1:1 повторена для lists, тож
   ризик такий самий низький, але явно не підтверджений живцем — варто
   архітектору перевірити перед прийняттям, якщо це критично.
2. `list-detail-page` не має власної кнопки «додати існуючий айтем у список»
   — за планом (задача 6) додавання йде ЛИШЕ зі сторінки айтема («Додати в
   список»). Це відповідає буквальному тексту кроку, але як UX-потік трохи
   незручно (створив список — і йди по кожному фільму окремо, щоб його
   наповнити); якщо це небажано, потрібне уточнення архітектора, а не мовчазне
   розширення скоупу.
3. Вакуум tombstones (Step 09, задача 6) НЕ розширено на колекцію `lists` —
   не було в задачах цього кроку; списки-tombstones накопичуються без
   автоочистки. Малий обсяг даних (списки не так часто видаляються, як
   nотатки-правки), тому не критично, але задокументовано як прогалину.
4. `lists.itemCount` в i18n навмисно без множинних форм (як і решта проєкту,
   напр. `settings.backup.hint`) — "{{count}} записів/entries/записей" завжди
   в одній формі, а не 1/2-4/5+ варіантах укр./рос. відмінювання.
