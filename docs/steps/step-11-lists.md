# Step 11 — Кастомні списки та «Улюблене»

**Передумови:** Steps 01–09 (потрібні: шар даних, UI бібліотеки, синк).
Прочитай `docs/ARCHITECTURE.md` §9 (Списки та шеринг) — модель і принципи там.

## Мета

Кастомні списки фільмів + прапорець «Улюблене» + похідні списки зі статусів.
Шеринг — НЕ тут (Step 12), але модель `ListEntry` вже містить його поля.

## Ключові інваріанти (з ARCHITECTURE §9 — перевіряються тестами)

- Список ≠ статус: будь-які операції зі списками НЕ міняють `status`/дані айтемів.
- Назви списків НЕ унікальні; ідентифікація тільки по `id` (uuid).
- Видалення списку — tombstone (`deletedAt`), як у айтемів; айтеми бібліотеки не чіпає.

## Завдання

1. **Міграція Dexie → version(2)**: нова таблиця `lists` (`id, updatedAt`),
   нове поле `favorite?: boolean` у MediaItem (без зміни існуючих записів —
   undefined = false). Індекси items не ламати. Тест міграції: база v1 з
   айтемами відкривається v2 без втрат.
2. `core/models/media-list.model.ts` — `MediaList`, `ListEntry` ТОЧНО за
   ARCHITECTURE §9.
3. `core/data/lists.repository.ts` (за зразком items.repository):
   - `lists` signal (без tombstones), `getById`, `create(name, description?)`,
     `rename`, `updateDescription`, `softDelete`, `restore`, `changedSince`;
   - `addEntry(listId, entryData)` — дедуп всередині списку по
     `tmdbId ?? itemId` (повторне додавання — no-op),
   - `removeEntry(listId, entryId)`,
   - `entryForItem(item)` — хелпер: MediaItem → ListEntry (snapshot полів).
   Всі мутації — через репозиторій, він ставить `updatedAt`.
4. **Улюблене**: у items.repository — `toggleFavorite(id)`; на картці
   бібліотеки і сторінці айтема — іконка-серце (токени, без Material-іконок,
   inline svg як у теми); фільтр «Улюблене» на сторінці бібліотеки.
5. **Похідні списки** (`features/lists/derived-lists.ts`, чиста функція +
   computed): «Хочу / Дивлюсь / Подивився / Кинув / Улюблене» — обчислюються
   з items, у UI виглядають як списки, але без редагування складу
   (склад = статуси/прапорці).
6. UI `features/lists/`:
   - роут `/lists`: секція похідних + секція кастомних (назва, к-сть, обкладинка
     з перших 4 постерів), кнопка «Новий список», rename/delete через меню
     (delete з confirm + снекбар «Відмінити»),
   - роут `/lists/:id`: записи списку. КОЖЕН entry резолвиться в бібліотеку
     по `tmdbId` (fallback: itemId для ручних) і показує ПОТОЧНИЙ статус юзера
     чіпом; entry без відповідника — бейдж «не в бібліотеці» + кнопка
     «+ в бібліотеку» (створює айтем want і лінкує). Видалення entry зі
     списку — хрестик, статуси не міняються,
   - на сторінці айтема: блок «У списках» (чіпи) + меню «Додати в список»
     (список існуючих + «створити новий»).
7. **Синк**: розширити SyncService і `/api/sync` на колекцію `lists`
   (ті самі pull/push/updatedAt/tombstone). Конфлікт поля `entries` —
   автоматичне об'єднання за `(tmdbId ?? id)` БЕЗ merge-діалогу (ARCHITECTURE
   §9); конфлікти name/description — через існуючий merge-діалог.
   Mongo: колекція `lists`, unique index `(userId, id)`.
8. i18n uk/en, мобільна верстка, оновити `/dev/ui` якщо з'явились нові
   shared-компоненти. Тести: інваріанти вище + дедуп entries + міграція +
   merge entries.

## Критерії приймання

- [ ] Два списки з однаковою назвою співіснують без конфліктів.
- [ ] Додав фільм у список → статус не змінився; видалив список → статуси на місці.
- [ ] Entry чужого по суті фільму (нема в бібліотеці) видно зі снапшота і додається кнопкою.
- [ ] Улюблене перемикається з картки і сторінки айтема, фільтр працює.
- [ ] Синк списків між двома браузерами працює; конфлікт entries зливається без діалогу.
- [ ] build/lint/тести чисті; процеси зупинені.

## Заборонено

- Ніякого шерингу/бекенд-ендпоінтів шерингу (Step 12).
- Не міняти механіку статусів і existing merge-діалог айтемів.
