# Журнал рішень (ADR-light)

Кожне архітектурне рішення — один запис. Нові рішення додаються знизу.
Виконавці НЕ змінюють прийняті рішення; якщо рішення не працює — пишуть сюди
пропозицію зі статусом «запропоновано» і зупиняються / роблять мінімальний обхід.

## 2026-07-11 — Зафіксовано з власником проекту

1. **Бекенд: Vercel Serverless Functions.** Обрано замість Render/Cloudflare:
   один репозиторій і деплой для фронта та api, безкоштовний тир, не «засинає»
   критично (cold start ~сотні мс — прийнятно).
2. **Auth: email + пароль (bcrypt + JWT).** Просто і зрозуміло друзям; без
   OAuth і refresh-токенів. Відновлення пароля — поза скоупом v1.
3. **UI: кастомна дизайн-система на CSS custom properties.** Angular Material —
   лише як функціональна база (діалоги, автокомпліт, меню, снекбар), повністю
   перетемізована токенами. Видимий дизайн — власний.
4. **Мови UI: українська + англійська**, runtime-перемикач, власний i18n-сервіс
   на signals (без ngx-translate і без build-time $localize — потрібен runtime switch
   і мінімум залежностей).
5. **Local-first: IndexedDB (Dexie) — головне сховище.** Хмара — опційна синхронізація.
   MongoDB Atlas напряму з браузера недоступна (Data API deprecated) → все через `/api`.
6. **Пошук: тільки TMDB як джерело видачі** (нуль дублікатів у результатах).
   Інші API (OMDb тощо) під'єднуються на сторінці деталей через imdbId.
7. **API-ключі тільки на бекенді** (proxy-ендпоінти), навіть для TMDB,
   хоч він і дозволяє браузерні виклики — щоб ключі не світились у бандлі.
8. **Синк: updatedAt + tombstones + ручний merge по полях** (див. ARCHITECTURE.md §6).
   Ніякого автоматичного last-write-wins для конфліктів «моїх даних».
9. **Видалення — soft (tombstone `deletedAt`)**, інакше синк «воскрешатиме» видалене.

## 2026-07-11 (пізніше) — уточнення від власника

10. **Тема — м'яка і темна.** Dark — дефолт і пріоритет; без чистих `#000`/`#fff`,
    приглушені десатуровані кольори, м'які радіуси й тіні. Деталі —
    ARCHITECTURE.md §8 «Напрям дизайну». Light — другорядна, теж м'яка.
11. **Папка дизайн-токенів — `web/src/app/design/`** (у §1 і §8 ARCHITECTURE
    спочатку були різні шляхи; зафіксовано за фактичним скаффолдом Step 01).
12. **Адаптивність — наскрізна вимога.** Кожен екран повноцінно працює на
    десктопі й телефоні (перевірка на 360px). Це критерій приймання кожного
    UI-кроку, а не окремий етап «потім». Деталі — ARCHITECTURE.md §8.

## 2026-07-11 — за результатами ревью Step 02

13. **i18n-пайп `t` — `pure: false` (підтверджено ревью).** Первинне
    припущення ARCHITECTURE §7 («сигнал тригерить CD, impure не потрібен»)
    було невірним: pure-пайп мемоізує по `key` і не перечитує сигнал.
    Impure-пайп у zoneless лишається signal-driven (CD запускає сам сигнал),
    тому це не «хак заради реактивності», а коректний паттерн. Деталі — §7.
14. **`/dev/ui` — постійна демо-сторінка дизайн-системи.** Не видаляється;
    кожен новий/змінений компонент `shared/ui/` додається на неї. У проді
    ховається guard'ом (Step 09), не видаленням.
15. **Агенти зобов'язані зупиняти всі свої процеси** (dev-сервери, watch)
    після завершення роботи — правило в CLAUDE.md «Після роботи».

## 2026-07-11 — Списки та шеринг (спроектовано наперед, Steps 10–11)

16. **Списки: uuid-ідентичність, назви НЕ унікальні.** Імпорт/створення ніколи
    не перезаписує по назві — завжди новий список. Список ≠ статус: операції
    зі списками не міняють статуси/дані айтемів ні за яких умов.
17. **Шеринг — snapshot, не жива синха.** Два транспорти: тимчасовий URL через
    бекенд (Mongo `shares`, невгадуваний код, TTL 30 днів, auth не
    обов'язковий) + офлайн base64-код (працює без мережі/бекенда). Статуси й
    оцінки відправника НЕ передаються ніколи; нотатки/лінки — тільки за
    явними чекбоксами (дефолт — вимкнено). В отримувача фільми показуються з
    ЙОГО статусами (резолв по tmdbId). Анонімний відправник — стабільний
    `anon-<id>`. Деталі — ARCHITECTURE §9, steps 11–12 (перенумеровано:
    власник вставив новий Step 10 — i18n en-дефолт + російська).
18. **«Улюблене» — прапорець `favorite` у MediaItem** (Dexie-міграція v2 у
    Step 11), а похідні списки (Подивився/Хочу/Улюблене…) обчислюються і
    шеряться так само, як кастомні.

## 2026-07-11 — Синхронізація (Step 08)

19. **Pull-курсор — СЕРВЕРНИЙ маркер `serverUpdatedAt`, не клієнтський `updatedAt`.**
    Клієнтські `updatedAt` йдуть від різних годинників; фільтрувати pull по них
    небезпечно (пристрій із відсталим годинником губився б). Сервер при кожному
    записі ставить власний `serverUpdatedAt`; курсор пагінації/`since` — саме він.
    Локальні зміни для push визначаємо окремим маркером `lastPushAt` (макс.
    `updatedAt` вже відправленого).
20. **Push захищений від гонки:** сервер не перезаписує, якщо його `updatedAt`
    новіший за присланий, а повертає свою версію в `conflicts[]`; клієнт зливає
    її ще раз. Клієнтські маркери синку НЕ рухаються, якщо лишились пропущені
    («Skip») конфлікти — інакше вони б загубились.
21. **Тест-інфра fake-indexeddb стабілізована** (тягли крихкість зі step-05/06):
    Dexie-база в тестах подається через `Dexie.dependencies` (не globalThis, бо
    раннер `@angular/build:unit-test` відновлює глобали між тестами), а
    `web/src/test-setup.ts` глушить ЛИШЕ конкретне безпечне teardown-відхилення
    leaked liveQuery. `npm test` тепер детермінований, exit 0.
22. **Синк — видимий і автоматичний** (вимога власника після Step 08):
    індикатор стану в хедері (не лише пункт меню), автосинк з debounce після
    мутацій + по `online`/фокусу; авто-режим НЕ відкриває merge-діалог —
    конфлікти показуються бейджем і вирішуються по кліку. Дизайн —
    ARCHITECTURE §6 «Автосинк і видимість», реалізація — step-09 задача 4г.
23. **Ехо-фільтр власного пуша при синку** (фікс ревью Step 09): маркер
    `sync.baseVersions` (id → updatedAt останньої узгодженої з сервером версії)
    відрізняє справжній конфлікт двох пристроїв від pull-луни власного пуша.
    Якщо один бік пари = вже узгоджена версія — це не конфлікт, беремо змінений
    бік без діалогу. Без цього редагування айтема ПІСЛЯ синку відкривало б
    хибний merge-діалог на наступному синку.
